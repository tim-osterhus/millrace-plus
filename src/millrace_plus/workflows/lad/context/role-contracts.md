# LAD role artifacts

Modified from the pinned role prompts, contracts and templates; see `PROVENANCE.md`. These are workflow-local data contracts, not a new Core protocol.

Read the ledger-selected `lad-state/active-role.json`, immutable occurrence `input.json` and `assignment.md`. The input freezes session/occurrence/role/lineage, original request digest, target source file digests, guidance digest, accepted inputs, specification, current packet/baseline/Fixer/review and pending Learning request. Write only the ledger-selected `lad-results/<occurrence_id>/result.json`, plus its evidence Markdown files. Foreground source is `target/`; Learning source access is read-only through its pinned foreground input. Never choose an arbitrary acceptance path.

The committed input provides `guidance_root`, `foreground_root` and `workspace_root`, derived by preparation from its validated workspace topology. Guidance lives durably in this occurrence's `lad-state/occurrences/<id>/guidance/`: its role prompt, four context files and six templates, copied from captured controls before READY. `guidance_files` pins every file; `guidance_snapshot_sha256` pins the exact manifest `{format:millrace-lad-guidance/v1,guidance_sha256,files}`, binding the snapshot to the full captured guidance identity. Verify that manifest and file hashes, then resolve context/prompts/templates beneath this guidance root. The snapshot survives preparation exit and does not depend on Core's temporary controls paths. Native adapters embed prompt text without injecting a controls directory, so never guess an invocation path. `accepted_input_refs` maps accepted occurrence IDs to their role, `foreground` or `learning` workspace, relative result path and result digest. Resolve each beneath the matching sibling workspace; request/specification/packet/baseline remain their independently pinned inputs. These are workflow-owned assignment files, not Core IDs or a generic invocation-context hook. Roles cannot modify snapshots.

`input_sha256` is SHA-256 of the parsed input object with its own `input_sha256` field removed, serialized by the existing `scripts/lad_state.py` `canonical` helper. Each `accepted_input_refs` entry's `sha256` is SHA-256 of the complete parsed referenced result object serialized by that same helper. Canonical JSON uses sorted keys, compact `(",", ":")` separators, `ensure_ascii=False`, `allow_nan=False`, and UTF-8 encoding, without a trailing newline. These two object identities are not hashes of the raw JSON file bytes. Markdown artifact `sha256` values remain hashes of the exact artifact file bytes.

Every result has exactly these fields:

```json
{"format":"millrace-lad-result/v1","session_id":"UUID","occurrence_id":"UUID","role":"recon","outcome":"PASS","lineage":"unpacketized","input_sha256":"64 hex from input","source_sha256":"SHA-256 of compact sorted-key JSON target path-to-file-digest map","guidance_sha256":"64 hex from input","artifacts":[{"path":"intake.md","sha256":"64 hex of exact file bytes"}],"findings":[],"human_evidence":null,"data":{}}
```

Echo every identity from the input. `source_sha256` must describe actual current target bytes after the role. Only Builder/Fixer/Troubleshooter/Updater may edit assigned packet paths. Read-only roles must leave target bytes unchanged. All result artifacts are relative to this occurrence result directory, regular contained `.md` files; aliases, duplicates and unsafe paths refuse. Each artifact echoes occurrence ID and contains substantive `## Evidence` and `## Outcome` sections, observed checks, exact identities and honest limitations. Required files below apply even to findings/errors/human-blocked; Checker errors/human-blocked may omit a not-yet-frozen baseline. Additional occurrence Markdown such as packet drafts is permitted and digest-checked. Accepted artifacts are immutable.

`findings` is an array of exact `{id,criterion,path,reproduction,evidence}` objects with stable IDs and original criterion references. Actionable findings require at least one; PASS requires none. `human_evidence` is null except HUMAN_BLOCKED/NO_SAFE_ROUTE, which require exactly `{type,obstacle,attempted,required_resolution}`. Type is one of `unavailable_input`, `human_choice`, `protected_work`, `budget_exhausted`, `diagnosis_exhausted`. Explain why already-authorized retrieval/repair cannot resolve the obstacle. A recoverable issue cannot become a passing artifact or an unsupported human hold.

Every ERROR variant includes `data.failure` with exactly `{operation,attempted,evidence,prerequisite_resolved}`; the first three are nonblank evidence strings, the last a boolean. ERROR_REPLACEMENT and ERROR_TRANSIENT_RESOLVED require true. No result authorizes replay of unknown effects.

| Role | Required Markdown | Additional data for accepted useful result |
| --- | --- | --- |
| Recon | `intake.md` | Map architecture, entrypoints, instructions, checks, integration boundaries, dirty ownership and reproduction. PASS → Planner; FINDINGS → Consultant; ERROR → Troubleshooter. |
| Planner | `specification.md` | PASS: `criteria:[{id,text,request_quote}]`; unique stable IDs, each exact nonblank quote occurs in the original request. Preserve this array unchanged on repair. Keep a sufficient original specification unchanged; add only necessary detail. No delegation. |
| Manager | `plan-check.md` plus every packet Markdown | PASS: `plan:[{id,lineage,criteria,depends_on,paths,input_refs,markdown}]`. Criteria are original IDs; dependencies are earlier lineages; paths are relative to target; `input_refs:[{occurrence_id,sha256}]` pin accepted results; markdown names an included occurrence artifact. Cover every criterion in the whole plan. Repair preserves original lineage set and unaffected accepted packets; `affected_lineages` identifies reopened packets only under the recorded remediation episode. |
| Builder | `implementation.md` | Implement only the current packet paths; evidence includes actual source/check results. PASS and FINDINGS_INSPECTABLE → Checker; uninspectable/error → Troubleshooter. |
| Checker | `baseline.md`, `review.md` | Freeze requirement-side baseline **before** reading implementation or Builder evidence. PASS: `criteria_checked` equals all packet criteria. Existing baseline reuse: `baseline` exactly echoes input baseline; only explicit new-baseline invalidation permits replacement. Stable findings belong to the frozen baseline. |
| Fixer | `repair.md` | `baseline` exactly echoes input baseline; `finding_ids` exactly preserves the input's assigned stable finding IDs. Later current-source regressions can add findings without rewriting the frozen expectations baseline. PASS/inspectable findings → Doublechecker. The independent acceptor records this inspectable repair identity. |
| Doublechecker | `review.md` | `baseline` and `fixer` exactly echo input; PASS includes complete `criteria_checked`. Evaluate the exact inspectable repair and current packet criteria. A same-baseline Updater invalidation can request review with null Fixer; that review creates no repair pair. Pair two inserts Learning, including a pass. Re-evaluation cannot add the same Fixer pair again. |
| Troubleshooter | `diagnosis.md` | PASS: `resume_role` equals exact saved role and `repair_verified:true`; requires the assignment's reserved local repair. PASS_REVIEW_REPAIRED → Doublechecker; prerequisite repair → enumerated saved-role replacement preparation; findings/error → Consultant. Unknown effects require reconciliation. |
| Consultant | `diagnosis.md` | REPAIR_SPEC/REPAIR_PACKETS consume the single planning-repair episode before Planner/Manager. REPAIR_EXECUTION requires exact interrupted role and remaining scoped repair. NO_SAFE_ROUTE needs human evidence. ERROR_REPAIRABLE → scoped Troubleshooter; ERROR_REPLACEMENT → guarded replacement. No diagnosis self-loop or self-approved scope expansion. |
| Updater | `completion.md` | PASS: `review` exactly echoes current input passing review, and `criteria_evidence` maps every packet criterion to nonblank observed evidence. Current source must still match review. Changed source must choose REVIEW_INVALIDATED_NEW_BASELINE or SAME_BASELINE. No commit/publication authority. |
| Learning | `assessment.md`, optional `candidate.md` | `pending_route` exactly echoes the pinned request's saved route. Assess two actual pairs; explain missing/unclear guidance, noncompliance or unrelated failure. Prefer no change if unsupported. Candidate stays separate and inactive. PASS/FINDINGS/error acknowledgement preserves the route. |
| Arbiter | `verdict.md` | `verdict:{criterion_id:{status,evidence}}` covers every original criterion exactly. Status is `pass`, `gap` or `unavailable`. PASS requires drained accepted plan and all criteria pass at actual source; FINDINGS reserves the one remediation episode and returns Manager. |

Arbiter FINDINGS requires a real, remediable gap in an original stable criterion;
each finding's `criterion` is an existing stable ID and the verdict must identify
the gap truthfully. An all-pass verdict is not a remediation gap. An operating or
process-constraint deviation outside the stable criteria that requires human
resolution uses HUMAN_BLOCKED, `human_evidence.type` of `human_choice`, and
`findings=[]`. Explain the obstacle, evidence checked, why source repair cannot
resolve it, and the required human decision. Keep stable verdicts truthful and
unchanged; do not invent IDs or relabel passing criteria as gaps to request repair.

Every role/outcome and dedicated acceptance route appears in `context/routes.md` and `workflow.json`. Dedicated expected-outcome nodes prohibit result/terminal mismatch. All semantic results, including errors and human holds, pass acceptance before routing. Transport/protocol errors/unknowns use explicit prepared replacement instead.

Invalid result examples: adding `"next_stage":"builder"` to the envelope adds an undeclared field and refuses; omitting `occurrence_id` refuses; using `"artifacts":"intake.md"` instead of an array refuses; returning Core PASS while `result.json` says FINDINGS refuses. Valid Core completion after writing the corresponding valid LAD envelope is `{"outcome":"PASS","summary":"Observed intake and reproduction recorded","refs":["lad-results/<occurrence_id>/result.json"]}`. Ref presence does not itself prove acceptance.

Before returning, verify exact identities/outcome, current source and guidance, required Markdown/digests, scope, original criterion mapping, baseline/pair references, evidence and unrun checks. Stop after one result. Deterministic guards own acceptance, routes, canonical state and completion.
