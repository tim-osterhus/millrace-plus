# Private Pi Workflow

`lad.full.pi@0.1` is an opt-in, private workflow package candidate in
`millrace-plus` `0.22.4`. It copies the accepted `lad.full`
workflow shape for a Pi RPC report channel and targets Core compatibility
`>=0.22.4,<0.23`.

The package contains no runtime branch, provider integration, model
configuration, credential, or live campaign. Source-level compilation,
export, and package admission checks use the independently reviewed Core
capacity contract. Retained predecessor wheel and sdist installations executed the
five-stage coding route described below using real stock Pi tools and a scripted
local provider.

## Preserved authority

The candidate keeps all seventeen selected stages and their existing queues,
artifact schemas, legal markers, terminal actions, routing, completion
behavior, capability declarations, and stop conditions. Each copied entrypoint
starts with the existing role prompt and appends a Pi-only instruction. The
appended instruction explicitly replaces the exact-observation-object
presentation rule for this variant while preserving every role, domain,
artifact, evidence, assumption, reference, gap, blocker, confidence, and
stop-condition obligation. The original `lad.full` graph remains unchanged;
the shared diagnostic handoff and Troubleshooter assets describe the source
context contract below for both variants.

The Pi Planner copy also recognizes the `lad.full.pi` dispatch identity in its
inherited `PLANNER_COMPLETE` learning-request fanout rule. The selected schema
and fanout continue to determine when those fields are required.

## Typed Manager dependencies

`planning.lad`, `lad.full`, and `lad.full.pi` declare the same task-card
dependency field, `depends_on_task_card_ids`. Each Manager card must include an
array of exact `task_card_id` values from that same artifact; `[]` means the
card is independent. Dependency relationships in a card body are explanatory
text and do not replace the typed field. The selected fanout keeps its existing
parent-source dependency and declares `execution.close_updater_complete` as
the final successful prerequisite action. Core ties that success to the
authenticated routed descendant of the exact original card; shared lineage,
another card's completion, an intermediate close, or a blocked close does not
establish a prerequisite's success. The selected workflows retain
assignment-level shared lineage.

The Pi workflow selects Pi-owned core-skill copies for Planner, Manager,
Mechanic, Auditor, Analyst, Professor, and Curator. Their examples use the
same three-field Pi result envelope as the selected Pi entrypoints, including
blocked outcomes with `null` artifacts where the selected terminal action has
no artifact schema. The selected artifact schemas, terminal markers,
observation routing fields, and stage duties remain those of `lad.full`.
`lad.full` continues to select the original shared core skills unchanged.

The Pi copy maps five authenticated runtime failure kinds: `timeout`,
`invocation_failed`, `result_parse_failed`, `output_too_large`, and
`result_rejected`. Seven execution roles (Builder, Checker, Fixer,
Doublechecker, Updater, Troubleshooter, and Consultant) route to
`lad_troubleshooter` under `execution.runtime_failure_recovery`. Six planning
roles (Recon, Planner, Manager, Mechanic, Auditor, and Arbiter) route to
`lad_mechanic` under `planning.runtime_failure_recovery`. The four learning
roles (Analyst, Professor, Curator, and Librarian) have no default mapping.

Only authenticated `ApplyRunnerRuntimeFailure` selects a mapped mechanical
recovery. It requires a settled authenticated failure: a failed adapter
completion or a completed candidate with an exact persisted semantic refusal.
For `result_rejected`, Millrace preserves the original candidate with its
`COMPLETED/SUCCESS` transport state. A separate persisted semantic refusal
supplies the typed failure.

Supported authenticated refusals may use the `result_rejected` mapping. Raw
candidate text cannot create a failure kind or its evidence. Pi command-level
timeouts cannot create typed failure evidence.

The component-free Pi path parses the exact three-key JSON envelope. The kernel then
applies the selected plan's declared outcome and action. Pi does not validate
`marker` against an authored enum.

An authored marker may name `RUNTIME_FAILURE` only when the selected graph
declares that outcome and an action for it. The kernel follows the declared
action under the finite policy. This authored marker does not become a typed mechanical failure. The
`RUNTIME_FAILURE` label alone does not make a marker runtime-owned. Unknown or
invalid candidates remain refused. Component-bound Millforge separately
validates provider result mappings.

A proven pre-external `invocation_failed` may map when recorded start intent
confirms there is no external owner and cleanup is `not_required`. Unclassified
or indeterminate start exceptions remain fatal. A stage invocation deadline
maps to `timeout` only after Millrace authenticates the settled completion and
confirms cleanup. Explicit user or global cancellation does not select the
typed mapping.

The recovery prompt receives a bounded, redacted diagnostic and recorded
source references through `governance_context.runtime_failure_source`. It
uses this handoff as evidence only. The handoff grants no authority or external
ownership. A semantic refusal or invalid candidate remains rejected. Recovery
cannot retroactively accept the candidate. Any later candidate must pass
normal selected validation.

Runtime-failure policies allow one immediate recovery attempt. They start a
15-minute cooldown at attempt 2 and quarantine at attempt 3. The runtime
refuses recovery if it cannot authenticate source evidence, or if the selected
policy or action is missing, inconsistent, or unsafe.

Diagnostic completion uses the selected `TROUBLESHOOT_COMPLETE` report route.
Its optional observation `resume_stage` chooses a declared execution target;
omitting it uses Builder. A runtime timeout may preserve the original task
without `qa_context`, so the selected COMPLETE projection preserves an existing
carrier exactly or derives the actual task contract and trusted work-payload
digest using the existing Builder BLOCKED expression. An unestablished Checker
baseline remains explicitly null. The agent does not manufacture this carrier.
The report follows its exact rendered schema, including optional
`learning_requests` only when that selected schema permits them.

`TROUBLESHOOT_RECOVERED` is a separate return to the latest recorded recovery
source, which may itself be a failed Troubleshooter. It is not an alias for
COMPLETE or a way to select an earlier Builder. The formal return and
quarantine markers are available only when their exact marker/artifact pairs
are rendered in `terminal_options` for the current recovery attempt; ordinary
Troubleshooter ingress uses only its ordinary rendered choices. The selected
policy and exact source/run/activation context remain authoritative, and the
terminal resolver checks that context again. Diagnostic success does not prove
product-task completion. Existing admitted plans retain their original
projection and asset pins, and previously rejected results remain rejected.
These source checks do not qualify a Linux/model run.

Runtime-rendered Troubleshooter choices are limited to actions eligible in
the selected state. Ordinary blocked-work ingress exposes its ordinary
`BLOCKED` and `COMPLETE` paths; attempt-owned return or quarantine choices
require the exact selected recovery policy, phase, source, run, and activation
context. The terminal resolver checks that context again, so an ineligible
marker is refused with its specific context error. These rules do not create a
separate ordinary quarantine action or per-card recovery lineage.

Each of the seventeen component-free `pi_rpc` runner bindings selects the
same Core-owned `runner_payload_capacity_pin` record. The bindings keep
`component_pin: null` and empty runner-produced `terminal_result_mappings`.
Thirteen execution and planning roles carry typed runtime-failure mappings.
The four learning roles have no default mapping.

The capacity pin does not create native component authority. The five declared
capabilities remain explicit: runner invocation, terminal intent, unrestricted
filesystem read, unrestricted filesystem write, and unrestricted process
execution. The package's `pi-rpc-terminal.md` file is inert and grants no
capability or selected workflow authority.

The selected completion behavior remains attached to
`lad_arbiter.millforge_runner` with its existing request, graph, evidence,
readiness, pass, gap, and blocked rules. No completion behavior, context,
budget, default, stage, graph, or outcome is dropped.

The `lad.full.pi` closure completion accepts an inline request body up to
`131072` bytes, raised from `16384`. Its `evidence_item_limit` stays `96`. Above
the inline ceiling, the `materialized_evidence_pages` policy applies. It uses
root `millrace-closure-evidence`, 32768-byte pages, an 8 MiB (`8388608`-byte)
full-snapshot limit, and a 1024-page limit. The complete sealed snapshot stays
in durable runtime state. Dispatch carries only a compact authenticated
projection of digests, sizes, and a page index. Millrace materializes the
session-owned pages as read-only files before start. Before any runner result is
accepted, the runtime re-verifies those pages. Drift, a missing page, or an
unreadable index refuses the result rather than accepting a verdict. Pages are
cleaned up after durable completion.

Requests beyond 8 MiB, 1024 pages, the projection limit, or 96 evidence items
are refused truthfully. The Pi prompt embeds the canonical body and the selected
overhead, and it must stay within the qualification config's 262144-byte
`max_input_bundle_bytes`. The Millforge-bound `planning.lad` and `lad.full`
variants keep their 16384-byte, schema 2 completion behavior, and their
component pins are unchanged. The evidence for this ceiling is offline source
and compile tests. It is not native-model or live-provider proof.

The trusted descriptor is the packaged Core file
`millrace/contracts/pi-rpc-payload-capacity.v1.json`, SHA-256
`dd7ef029fed5aeebbbb08081934e881e8ed9baecbcf87ba1d03a39d1ffe75d36`.
Its exact capacity is `1,048,576` bytes and its adapter kind is `pi_rpc`.
The selected nested record is schema version `1` for contract
`millrace.pi-rpc.payload.v1` and carries that exact descriptor digest.
Plus selects the record returned by
`payload_capacity_pin_record(installed_payload_capacity_pin())`; it does not
invent a capacity from workflow text, local configuration, or a native
component pin. Core revalidates the installed descriptor at compile, export,
admission, reload, and Pi start boundaries.

A Pi stage returns one complete JSON object with exactly these top-level keys:

```text
marker
artifact_payload_candidate
observation_payload_candidate
```

The selected artifact schema is copied into `artifact_payload_candidate`. The
existing observation routing fields keep their established names. Narrative
evidence is carried in the optional generic
`observation_payload_candidate.runner_report` string when the selected stage
has narrative obligations. The string is bounded and redacted by the adapter;
it has no identity, grant, marker, result, routing, usage, cleanup, or terminal
authority. No fourth key, unknown key, prose, fence, second artifact, or
nonfinite number is admitted.

## Qualification boundaries

The capacity correction closes the prior source-level completion-capacity
blocker for the component-free Pi LAD binding. The positive checks here show
that the reviewed source compiles, exports, and is admission-ready while
retaining completion behavior.

The private local qualification uses Core's explicit Pi profile v2 with a pinned
observer and private pipe. It covers per-command process groups in trusted Darwin
workspaces and one pinned Ubuntu 24.04 x86_64 installation; escaped descendants remain outside the guarantee. Maximum ordinary
filesystem/process permissions and no tool approvals are the profile default.
Uncertain execution is refused even when a later command succeeds; resource
disposal is a separate result.

Six of the seventeen Pi bindings use nested schema version 6. The other
eleven use version 4. All seventeen retain the Core-owned payload-capacity
pin. Thirteen execution and planning roles map the five supported runtime
failure kinds. The four learning roles have no default mapping.

The package compatibility range remains `>=0.22.4,<0.23`. The range does not
prove support for these schemas or runtime behavior. Qualify against the
repaired 0.22.4 Core artifact by exact digest. Earlier private artifacts and
installed generations remain separate frozen evidence.

Retained predecessor wheel and sdist installs executed Recon, Builder, independent
Checker, Updater and automatic closure Arbiter. Builder observes a failing test,
edits through Pi and reruns the identical command successfully. The test remains
unchanged. Public runtime state records the five accepted actions and a passed,
closed closure target. This qualifies that route, not every selected stage or the
Fixer/Doublechecker branch. The provider is scripted. The final 0.22.4 artifacts, real-model behavior,
production provider accounting, other Linux installations and the historical
three-arm comparison still require their respective qualification.
